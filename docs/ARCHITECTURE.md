Документ фиксирует решения, которые **дорого менять потом**. Всё остальное
(экраны, контент, визуал) — дёшево переделать на любом этапе.

## 1. Стек

| Слой | Выбор | Почему |
|---|---|---|
| UI + рантайм | **Flutter (Dart)** | Android + iOS из одного кода, Wear OS поддерживается. Собственный рендерер — премиум-анимации и кастомные графики (радар, кривая деградации) идут 60 fps без DOM. Плагины Firebase / AdMob / RevenueCat / Health Connect — первого класса. |
| Локальная БД | **Drift (SQLite)** | Source of truth. Приложение обязано работать офлайн — это ядро продукта, а не фича. |
| Бэкенд | **Firebase** (Auth, Firestore, Functions, Remote Config, Crashlytics) | 0 $ до десятков тысяч MAU, нативно дружит с Google Play. |
| Подписки | **RevenueCat** | Прячет ад Google Play Billing + StoreKit. Кроссплатформенный статус премиума из коробки. |
| Реклама | **AdMob** (только нативный баннер) | См. §6 — правила размещения. |
| Стейт | **Riverpod** | Компилируемо-безопасный DI, легко тестировать, не требует контекста. |
| Навигация | **go_router** | Deep links нужны для «вызова другу» и шаринга результатов. |

### Про часы — честно

**Ни один** кроссплатформенный фреймворк не покрывает watchOS. Реальность:

- **Wear OS** — Flutter работает, переиспользуем ~90 % кода. Планово в v1.2.
- **watchOS** — только отдельное приложение на SwiftUI. Переиспользовать получится
  *протокол данных и формулы*, но не UI. Планово в v1.3, если iOS покажет выручку.

Именно поэтому §2 требует держать доменную логику в чистом Dart-пакете: это
единственное, что делает будущий порт на часы дешёвым.

```

  tmb_domain/          ← ЧИСТЫЙ Dart. Ноль импортов Flutter.
```

## 3. Модель данных — главное решение проекта

Приложение обязано с **первого релиза** писать **сырые события**, а не агрегаты.

```
Session
  id, startedAt, endedAt, location(HOME|GYM|OUTDOOR), difficulty, appVersion
  ├─ RoundLog        (по одному на круг)
  │    roundIndex, durationMs, rpe?
  │    └─ ExerciseSet  (по одному на упражнение в круге)
  │         exerciseId, unit(reps|seconds), prescribed, done, startedAt, endedAt
  └─ TaskAttempt     (по одному на КАЖДУЮ когнитивную попытку)
       roundIndex, taskId, packId, packSource(builtin|imported|user),
       archetype, domain, difficulty, isCorrect?, selfRating?,
       latencyMs, presentedAt, answeredAt, payloadHash
```

`isCorrect` — `null` у непроверяемых задач; `selfRating` (0–3) заполняется только у
них. `ExerciseSet` — отдельная запись **на упражнение**, а не агрегат по кругу: без неё
невозможна прогрессия нагрузки (§10), а восстановить её задним числом нельзя.

**Почему это критично.** Ключевая фича продукта — «кривая деградации когнитивных
функций»: как падает точность и скорость мышления от круга к кругу. Её **невозможно
восстановить задним числом** из агрегатов вроде «решено 12 из 15». Если v0.1 не пишет
`latencyMs` и `roundIndex` для каждой попытки, то вся аналитика v0.3 и все лидерборды
v0.5 стартуют с нулевой историей у существующих пользователей.

Поэтому: **полное логирование событий входит уже в v0.1**, до того как появится хоть
один экран аналитики.

Дополнительно:
- Все ID — UUID v4, генерируются на клиенте. Это делает офлайн-запись и последующий
  merge с сервером бесконфликтными.
- Схема Drift версионируется с миграциями с самого первого релиза.
- `payloadHash` — хеш условия задачи; нужен, чтобы сервер мог проверить, что клиент
  не подменил задачу на тривиальную (§4).

## 4. Индекс Оперативника и защита лидербордов

Формула ранжирования. Считается **на сервере** (Cloud Function) из сырых событий:

```
Физика      = Σ(повторения × вес_упражнения × множитель_сложности)
Когниция    = точность × скорость_норм × вес_типа_задачи
Стойкость   = точность_последнего_круга / точность_первого_круга   ← ядро продукта
Индекс      = (Физика × 0.4 + Когниция × 0.4) × (0.7 + 0.6 × Стойкость)
```

«Стойкость» — то, ради чего приложение вообще существует: она награждает не самого
сильного и не самого умного, а того, кто **сохраняет мышление под нагрузкой**.

**Античит (обязателен до публичных лидербордов в v0.5):**
- Клиент **никогда** не отправляет свой счёт. Он отправляет сырые `TaskAttempt` и
  `RoundLog`; Function пересчитывает индекс сама.
- Отсечка нереалистичных значений: `latencyMs < 250` для математики = бот.
- Правило физической правдоподобности: круг из 40 берпи за 30 секунд отклоняется.
- Firestore Security Rules: коллекция `leaderboards` доступна клиенту **только на чтение**.

## 5. Локализация — с первой строки кода

Мультиязычность стоит в v0.6 как *премиум-фича*, но заложить её надо в v0.1, иначе это
переписывание всего контента.

- Интерфейс: `flutter_localizations` + ARB-файлы. Ни одной строки в коде виджета.
- **Контент когнитивных задач — не строки в ARB, а данные.** Задачи вида «опишите
  комнату, не используя слов с буквой О» **непереводимы дословно** — в английском
  нужна другая буква, другая логика. Поэтому пул задач лежит в
  `assets/content/<locale>/*.pack.json` и пишется под каждый язык отдельно.
- Стартовые локали: `ru`, `uk`. Далее `en`, `de`, `es` (v0.6).

обновлением контента и ежемесячным.

## 7. Правила размещения рекламы (продуктовый инвариант)

Пользователь платит вниманием только там, где это не мешает. Жёстко:

- ✅ Нативный статичный баннер — **только** на дашборде и в архиве миссий.
- ❌ **Никогда** во время физической фазы и во время когнитивной паузы.
- ❌ Никаких interstitial, никаких rewarded-видео, никакого автоплея.
- ❌ Ничего кликабельного в зоне большого пальца во время тренировки — это и UX-провал,
  и риск бана за accidental clicks по политике AdMob.
- Премиум — снимает рекламу полностью.

## 8. Приватность и Play-политика (риски, а не формальность)

- Приложение собирает данные о здоровье и фитнесе → обязательна **Data Safety**-форма
  и политика конфиденциальности **до** первой загрузки в консоль.
- Health Connect требует отдельного объявления разрешений и ревью Google.
- Фоновая геолокация (v0.3, маршруты) — самое строгое ревью в Play. Если получится,
  используем foreground-only location: этого достаточно для трекинга во время сессии
  и снимает почти весь регуляторный риск.
- Никаких медицинских утверждений в описании («улучшает когнитивные функции»,
  «лечит») — это прямой путь к отклонению.
- Соцфичи (чат в сквадах) → нужен механизм жалоб и модерации, иначе бан по UGC-политике.
  Поэтому в v0.5 чат — **не** свободный текст, а набор пресетов («Салют», «Вызов»).

## 10. Решения от 2026-11-19: категории, свой контент, прогрессия

Появились из требований владельца ([REQUIREMENTS.md](REQUIREMENTS.md)). Пункты D4 и D5
ждут подтверждения владельца — до него это рекомендации, а не инварианты.

**D1. Неопределённость — свойство контента, а не восьмой архетип.** Инвариант 3
остаётся: механик семь. Задачи на неопределённость живут в домене `cog.uncertainty.*`
и ложатся на `verbal`, `recall` (с допуском) и `stream`. Подробно —
[UNCERTAINTY.md](UNCERTAINTY.md).

**D2. Разделы и категории.** Раздел — производное от `verifiable` («Проверяемые» /
«Непроверяемые»). Категория — путь `domain` (`cog.uncertainty.rule_shift`), её название
лежит в самом паке. Включённость хранится в **профиле пользователя**, не в паке, как
множество *отключённых* путей: новые категории из обновления паков включены по
умолчанию. Отключённый родитель отключает потомков; последнюю категорию отключить
нельзя — пул не бывает пустым.

**D3. Канонический формат обмена — JSON** с `schemaVersion`. Именно его выдаёт ИИ-чат
стабильнее всего, и Dart читает его без пакетов. YAML в документах — только для
читаемости примеров.

**D4. Пользовательский и импортированный контент (`packSource != builtin`) исключён из
Индекса и лидербордов.** Клиент способен написать себе тривиальные «проверяемые»
задачи, а `payloadHash` от этого не защищает. События по такому контенту пишутся как
обычно: личная кривая деградации работает. Это следствие инварианта 8.

**D5. Импорт — недоверенный ввод.** Только plain text (без HTML и автооткрытия
ссылок), лимиты на размер файла, число элементов и длину строк, валидатор **до**
записи, предпросмотр («новых 40, дублей 3, ошибок 2»), дедупликация по `id` и хешу.
Импортированный пак — единица удаления: откат целиком одним действием.

**D6. Прогрессия — чистая функция в `tmb_domain/progression/`**:
`nextPrescription(history, now, profile) → Prescription`. Без Flutter, без I/O,
покрывается юнит-тестами. План сессии **фиксируется при старте** и пишется в лог
(`ExerciseSet.prescribed`); внутри сессии он не подстраивается — иначе кривая
деградации измеряла бы наш алгоритм, а не усталость (см. EXTENSIBILITY §9). Всегда
отдаёт причину одной строкой («4 дня отдыха → +2»), включается и выключается,
допускает ручную правку.

**D7. Данные — в v0.1, алгоритм — в v0.2.** `ExerciseSet` пишется с первого Flutter-
релиза, даже если подстройки нагрузки ещё нет: к v0.2 у пользователя уже накопится
история, на которой алгоритм сразу работает.

## 11. Решения от 2026-11-19: слой данных и движок (v0.1)

**D8. `tmb_data` не открывает базу.** Схема Drift и репозитории принимают
`QueryExecutor` снаружи; открывает его приложение (`drift_flutter`:
`TmbDatabase(driftDatabase(name: 'tmb'))`, один экземпляр на приложение).
Причина — инвариант 1 и `invariants.yml`: в `lib/` слоя данных нет `dart:io`, а значит
пакет остаётся переносимым. Сгенерированный код (`*.g.dart`) коммитится, CI
`build_runner` не запускает.

**D9. Запись по ходу сессии.** События пишутся через `appendEvents`, а не одной
пачкой в конце: убитое приложение не теряет попытки. Незавершённая сессия остаётся
`endedAt = null`. Это же основа кривой деградации — сырые события дороже агрегатов.

**D10. Миграции — с первой версии, откат запрещён.** `schemaVersion = 1`, дамп схемы в
`drift_schemas/`, тест «от каждой версии до текущей». Открытие базы более новой версии,
чем приложение, — `DatabaseDowngradeException`, а не тихая порча.

**D11. Движок сессии — чистая машина состояний с внешним временем**
(`tmb_domain/engine/`): ни таймеров, ни `Future`/`Stream`, ни часов. UI подаёт
`nowMs` и показывает `EngineState`; всё, что движок записал, — готовый `EventsExport`.
Контракт воспроизводимости — SCHEMAS §9, решения 29–33.

**D12. Каркас приложения (`apps/mobile`).** Riverpod (провайдеры — `lib/data/`),
go_router (маршруты и пути — `lib/app/router.dart`, экраны сессии и настроек — в
`lib/features/`). Встроенные паки остаются в `assets/content/` в корне репозитория
(их валидирует CI); в бандл они попадают через симлинк `apps/mobile/assets/content`,
потому что Flutter молча игнорирует ассеты вне каталога пакета. Загрузчик
(`ContentLoader`) прогоняет каждый пак через доменный валидатор, ошибка — громкая.
Каталоги ассетов не рекурсивны: новая локаль требует строки в `pubspec.yaml`.

**К решению до v1.0:** удаление «всех данных пользователя» (приватность, Data Safety);
сейчас есть только `deleteSession`.

**D13. Круг пишется при закрытии окна оценки.** В `SessionRepository` нет обновления
`RoundLog.rpe`, поэтому круг и его подходы сохраняются один раз — когда оценка дана или
окно закрыто (следующий подход, конец сессии, эвакуация). Попытки задач пишутся сразу.
При убитом приложении теряется не более текущего и последнего неоценённого круга.
Чтобы писать по одному подходу, нужен `rateRound(roundId, rpe)` в репозитории.

**D14. Уход приложения в фон — пауза сессии, время считается по монотонным часам.**
`hidden`/`paused` (сворачивание, гашение экрана) останавливают время движка; `inactive`
(шторка, системный диалог) — нет. Возврат сам не продолжает: экран закрыт заглушкой
(тот же значок и подпись фазы, условие задачи скрыто, цифры и выбор сохраняются) с кнопкой
«Продолжить» и «Эвакуацией». Время паузы вычитается целиком: `latencyMs` и сроки её не
видят. Реализовано в `SessionController` без правок движка: время движка =
`старт по clockProvider + монотонные мс − замороженное` (`sessionMonotonicClockProvider`),
поэтому смена системных часов сессию не ломает. Цена: метки `presentedAt`/`answeredAt`/
`endedAt` событий лежат в «активном» времени и после пауз отстают от настенных часов;
`Session.startedAt` настоящий, `endedAt` в БД восстанавливается с учётом D15. Если
понадобится настоящее wall-время в событиях — `pause`/`resume` переезжают в движок.

**D15. Когнитивное окно держится до срока.** Источники: DESIGN (экран 03: «кнопка
следующего круга заблокирована до конца паузы»), прототип (`breakSeconds: 180` — фиксированный
таймер), UNCERTAINTY (пауза по умолчанию 180 с, задача 60–120 с). Планировщик кладёт в окно
одну задачу (`tasksPerCognitiveBlock = 1`), поэтому без удержания окно кончалось за 20–60 с и
отдых между кругами пропадал. Теперь, когда задачи разобраны раньше `durationSec`, экран
показывает остаток паузы (оранжевая фаза, радар-таймер, итог последней задачи, заблокированная
кнопка), а следующий этап стартует по таймеру. Движок тут не менялся: пока удерживается окно,
его часы заморожены (как при паузе), а удержание — часть сессии и возвращается в
`Session.endedAt`. Попытки пишутся как раньше; пауза приложения внутри удержания остаток не съедает.
Вариант «тянуть больше задач в окно» отвергнут: он меняет контент сессии и поток данных ради
сохранения таймера, которого и так требует дизайн.

**Что не хватает движку и данным (по итогам первых экранов, решить к v0.2):**
`finishSpeech(now)` для `verbal` (иначе `latencyMs` включает самопроверку), `availableInventory` в
профиле, `package_info_plus` для настоящего `appVersion`, перенос перемешивания
`choice`/`ordering` (SCHEMAS, решение 27) из `features/session/task_order.dart` в домен.

## Сводка сессии для виджета

Фундамент под нативный виджет домашнего экрана (v0.2+): по фиксации сессии
приложение пишет **одну компактную сводку последней сессии** в простое key-value
хранилище, которое умеет читать нативный код. Сам виджет — позже.

**Формат** — `SessionSummarySnapshot` (`tmb_domain/summary/`, чистый Dart),
JSON под `kind: "session_summary"`, `schemaVersion: 1`:

| Поле | Смысл |
|---|---|
| `sessionId`, `startedAt`, `utcOffsetMin`, `localDate` | идентификатор, старт (мс UTC), пояс и готовая локальная дата `YYYY-MM-DD` |
| `status` | `completed` (`endedAt` записан) или `aborted` |
| `durationMs` | у прерванной — по последнему событию (решение 32) |
| `rounds`, `setsTotal`, `setsDone` | круги; подходы всего / с `done > 0` |
| `verifiableAttempts`, `correct`, `accuracy` | только машинно-проверяемые; таймаут и пропуск — «не верно»; `accuracy` = `correct / verifiableAttempts`, `null` без задач |
| `averageLatencyMs` | среднее по отвеченным проверяемым; `null` без ответов |

`accuracy` и `localDate` лежат в JSON готовыми для нативного читателя, при чтении
игнорируются и пересчитываются. Читатель обязан игнорировать неизвестные поля и
отвергать `schemaVersion` выше известной; изменение смысла поля — новая версия.

**Хранение.** `SessionSummaryStore` (`tmb_data`: `read` / `write` / `clear`) и
реализация на `shared_preferences` в приложении: одна строка JSON под ключом
`tmb.last_session_summary` (на Android — файл `FlutterSharedPreferences`, ключ
`flutter.tmb.last_session_summary`). Имя ключа — контракт с виджетом. Drift не
взят сознательно: виджет — отдельный процесс, а SQLite-файл с миграциями и
WAL читать из нативного кода дороже и хрупче, чем одну строку; Drift остаётся
источником правды, сводка — производная витрина и пересобирается из него.
iOS (App Group) и Wear — отдельная реализация того же интерфейса.

**Почему так.**
- `verbal` не участвует вовсе (инвариант 7), Индекса и счёта в сводке нет —
  клиент их не считает и не отправляет (инвариант 8): это числа для показа.
- Расчёт живёт в домене (`VerifiableTally`, `sessionDurationMs`), а не в UI:
  его переиспользуют будущие порты. `SessionStats` приложения считает то же
  самое для экрана итогов и со временем должен делегировать этим функциям.
- Запись — на уровне репозитория: `SummaryRecordingSessionRepository`
  оборачивает `SessionRepository`; `finishSession` (завершённая сессия) пишет
  сводку, `deleteSession` стирает её, если она указывала на удалённую сессию.
  Обращение к хранилищу идёт в фоне и не задерживает экран итогов; сбой
  не ломает запись в БД, только репортится. Прерванная сессия `finishSession`
  не проходит — её фиксирует вызов `recordSessionSummary(store, bundle)`
  из контроллера.
